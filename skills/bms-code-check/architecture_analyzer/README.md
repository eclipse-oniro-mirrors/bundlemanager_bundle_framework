## 📖 架构分析维度

### 1. 分层架构分析

**目的**: 检查代码分层是否合理，是否存在层级混乱

**检查项**:
- 是否有明确的分层（UI层、业务层、数据层）
- 是否存在跨层调用
- 是否有循环依赖
- 职责是否清晰

**常见问题**:
- UI层直接访问数据库
- 业务逻辑散落在多层
- 缺少明确的接口定义

### 2. 依赖关系分析

**目的**: 识别模块间的依赖关系是否合理

**检查项**:
- 是否存在循环依赖
- 依赖方向是否正确（高层依赖低层）
- 是否有过度耦合
- 接口稳定性

**常见问题**:
- 模块A依赖模块B，模块B又依赖模块A
- 底层模块依赖高层模块
- 修改一个模块影响多个其他模块

### 3. 模块化设计评估

**目的**: 评估代码的内聚性和耦合度

**检查项**:
- 单一职责原则
- 高内聚低耦合
- 模块边界清晰
- 接口设计合理

**常见问题**:
- 一个类承担多个职责
- 修改一处需要改动多处
- 模块间通过实现类直接耦合

### 4. 接口设计评审

**目的**: 评估 API 和接口的设计质量

**检查项**:
- 接口简洁性
- 接口完整性
- 版本兼容性
- 错误处理机制

**常见问题**:
- 接口过于复杂
- 缺少必要的接口
- 接口变更导致兼容性问题

### 5. 设计模式识别

**目的**: 识别设计模式和反模式

**检查项**:
- 正确使用设计模式
- 识别反模式（如God Object、Spaghetti Code）
- 设计模式适配场景

**常见问题**:
- 滥用设计模式
- 在不合适的场景使用模式
- 缺少必要的抽象

### 6. 性能架构分析

**目的**: 识别性能瓶颈和优化点

**检查项**:
- 数据访问效率
- 算法复杂度
- 资源使用
- 并发处理

**常见问题**:
- N+1 查询问题
- 不必要的锁竞争
- 内存泄漏风险

## 🛠️ 使用方法

### 进行架构评审

1. **准备阶段**
   ```bash
   # 阅读架构分析指南
   cat code_architecture_analyzer.md

   # 了解检查清单
   grep -A 100 "架构检查清单" code_architecture_analyzer.md
   ```

2. **评估阶段**
   - 按照六个维度逐项检查
   - 记录发现的问题
   - 评估问题严重程度

3. **报告阶段**
   - 生成架构评审报告
   - 提供改进建议
   - 制定优化路线图

### 代码审查中的架构检查

在 PR 审查时关注：

1. **架构影响**: 这个改动是否影响整体架构
2. **依赖变更**: 是否引入新的依赖或破坏现有依赖
3. **接口变更**: API 变更是否合理
4. **设计模式**: 是否正确使用设计模式
5. **性能影响**: 是否有性能风险

## 📊 架构质量度量

### 评分标准

| 维度 | 权重 | 评分标准 |
|------|------|----------|
| 分层架构 | 20% | 层次清晰、无跨层调用 |
| 依赖关系 | 20% | 无循环依赖、依赖方向正确 |
| 模块化 | 20% | 高内聚低耦合 |
| 接口设计 | 15% | 简洁完整、稳定可靠 |
| 设计模式 | 15% | 正确使用、无反模式 |
| 性能架构 | 10% | 高效、无瓶颈 |

### 质量等级

- **A级 (90-100)**: 优秀的架构设计
- **B级 (80-89)**: 良好的架构设计，有改进空间
- **C级 (70-79)**: 一般的架构设计，需要优化
- **D级 (60-69)**: 较差的架构设计，急需重构
- **E级 (<60)**: 不可接受的架构设计

## 🚀 优化建议

### 常见优化方向

1. **重构分层架构**
   - 识别并拆分混乱的层级
   - 建立清晰的层次边界
   - 定义接口规范

2. **解决依赖问题**
   - 使用依赖注入
   - 引入中间层解除循环依赖
   - 定义清晰的模块接口

3. **提升模块化**
   - 提取公共服务
   - 划分清晰的模块边界
   - 减少模块间耦合

4. **改进接口设计**
   - 简化接口
   - 增强接口稳定性
   - 完善错误处理

5. **应用设计模式**
   - 识别适用场景
   - 正确实现设计模式
   - 避免反模式

6. **优化性能架构**
   - 优化数据访问
   - 减少锁竞争
   - 引入缓存机制

## ❓ 常见问题

### Q1: 架构分析会不会太复杂？

**A**: 不会。本 skill 提供了系统化的方法和检查清单，可以逐步学习和应用。建议从基础检查开始，逐步深入。

### Q2: 如何平衡架构设计和开发速度？

**A**: 架构设计是为了长期的可维护性。在项目初期投入适当的架构设计时间，可以大大减少后期的维护成本。

### Q3: 什么时候需要重构架构？

**A**: 当出现以下情况时需要考虑重构：
- 新功能开发变得困难
- 修改一个 bug 影响多个模块
- 代码重复度高
- 性能问题严重
- 团队成员普遍反映代码难以理解

### Q4: 如何说服团队进行架构优化？

**A**:
1. 用数据说明问题（如修改影响范围、bug 率）
2. 提供具体的改进方案
3. 展示优化后的收益
4. 分阶段实施，降低风险

### Q5: 架构分析是否需要特殊工具？

**A**: 不一定。虽然有一些架构分析工具，但本 skill 提供的方法主要依靠代码审查和人工分析，更适合大多数团队。
